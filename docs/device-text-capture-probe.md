## 3. 三方证据链

| 证据源 | 结果 |
|---|---|
| 串口日志（5 轮对话全量）| ❌ STT 文本、TTS 文本、JSON 载荷、session/turn/speaker 标识——全部为零 |
| 设备屏幕（**照片识图确认**，2026-11-20 用户拍摄）| ✅ **聊天气泡渲染 AI 回答原文**：「爸爸好呀，怎么听着有点没精神，是没睡好吗？」，"打断"按钮高亮=正在播报中 |
| 官方协议文档（websocket_zh.md）| ✅ 文本下发是标准协议消息，不依赖特性开关 |
| 上游源码（xiaozhi-esp32 831ffd1）| ✅ 原版固件默认就打文本日志：application.cc L686 `ESP_LOGI(TAG, "<< %s")`（TTS）、L702 `">> %s"`（STT）；trae_card 魔改日志层时丢弃了这两行（tag 改为 "xiaozhi"、增加自研统计行、无任何 "<<"/">>" 输出）|

**四方对齐的结论：文本确实下发到了设备、固件协议层确实接收并处理了（渲染上了屏）、只是 trae_card 改写日志层时丢弃了文本输出。**

> 屏幕观察过程备注（诚实性）：用户对屏幕是否有文字先后给出三次相互矛盾的说法（无→有→无），最终以照片识图为准（有文字）。照片仅证实 **AI 侧气泡**；用户说话的回显（STT 上屏）未在照片中出现，STT 文本到达性由协议文档+上游源码推定，待改固件后实测确认。

协议文档关键引文（server → device 方向，均为标准消息）：

```json

{"session_id":"xxx","type":"tts","state":"sentence_start","text":"..."}
```

**三方对齐的结论：文本确实下发到了设备、固件协议层确实接收并处理了（渲染上了屏）、只是固件不往串口日志打印。**

## 5. 结论说明

**零改固件：不可行（已证死）。** 多轮对话的串口全量日志中不存在任何文本；屏幕文本与串口日志的差异证明这是固件的日志策略，不是消息缺失。

**改固件：可行且改动量小。** 方案：在 MQTT 协议消息处理回调中（`stt` 消息与 `tts sentence_start` 消息分支，对应 xiaozhi-esp32 协议代码的 `OnIncomingJson` 路径）加 `ESP_LOGI` 输出 `session_id` 与 `text` 字段。**具体补丁形态、采集适配器设计、风险清单见 `firmware-text-log-patch.md`。** 风险与前置条件：

1. **需要 trae_card 的源码**。设备固件标注 2.1.0-xiaozhi.29，若源码可得（Trae 项目仓库？），改动+编译+刷机即可；若不可得，需向上游 xiaozhi-esp32 对齐协议层后自建，工作量大得多。
2. **串口日志含儿童对话明文** → 采集适配器必须本地脱敏/加密落盘（任务书约束 3 的延续）。
3. **session_id 可选下发**：协议文档注明"服务器可选下发 session_id"——实测日志无法判断这台设备的云是否下发。改固件后若 session_id 为空，需靠本地轮次计数配对。
4. **OTA 兼容**：小智有 OTA 机制，改版本号/签名策略需留意，避免设备被云端 OTA 覆盖回官方固件。

**替代路线（零固件改动，供决策参考）**：屏幕实际渲染了完整文本——理论上"拍屏"也能拿到文本，但作为长期采集方案不现实；文本同时存在于小智云服务端，云端对话历史/控制台导出（若开放）是另一条待验证路线，不在本任务范围。

## 6. 任务书 §六 诚实性自查

1. **"看到文本"vs"稳定重建"**：串口层面连"看到"都做不到（0 条）；屏幕层面为单次人工目视确认"完整"，未做逐句核对。若走改固件路线，第一步应验证文本完整性（长回答的 sentence_start 是否逐句齐全）。
2. **"日志没打"vs"消息没收到"已判明**：屏幕渲染 + 协议文档双重证据 → **消息到了，日志没打**。此判定不依赖对日志级别的猜测。
3. **未为完成任务改动固件**：全程只做 RTS 复位（2 次）与串口只读监听，未刷机、未改配置、未改云端地址。

## 7. 附带发现（对后续开发有用）

- **自动休眠**：约 2 分钟无交互进入待机（`standby online=1 mic=0`），约 5 分钟深度休眠至 USB 掉线。采集适配器必须处理设备的周期性离线。
- **小智云可用性**：测试窗口内两次累计约 20 分钟连接故障（TCP 层 sock<0），设备侧重试+网络栈重启可自愈。采集系统需容忍云抖动。
- **MQTT 保活节奏**：TLS 证书校验约每 55 秒一次（即 MQTT keepalive 周期）。
- **本机复现命令**：看门狗式串口捕获（设备唤醒自动续抓）见 `D:\dsh\logs\serial-watch-*.log` 采集脚本（本文档执行时的原始日志存于同目录，仅含结构无对话明文）。
